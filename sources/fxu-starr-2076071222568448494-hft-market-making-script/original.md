## 原帖在讲什么

作者补发一篇被小红书封掉的原帖，主题是一个已经跑出结果的高频做市策略脚本结构，以及作者理解中的做市脚本开发设计模式。

核心做法是先把脚本结构写成注释 `Label`，把每一步规划成文档，再拆成模块，由 `AI` 对照 `Label` 逐条实现。

## 脚本结构整理

### 1. 市场数据层

脚本首先从框架里获取市场数据。

数据包括但不限于：

- `trades`
- 多档 `orderbook`
- `BBO`
- 多交易所市场数据

如果策略需要跨交易所，就为每个交易所写对应的数据获取模块。

### 2. 计算层：bucket / bin、alpha 与 forecast midprice

作者建议开 `bucket` 或 `bin` 来计算 `alpha` 和其他特征函数，例如交易强度。

拿到定量数据后，再用自己的方法路径，把 `alpha` 加到当前 `midprice` 上，得到 `forecast midprice`。

作者当前使用的是：

- 高频时序定时计算；
- 线性调整；
- `fair value * alpha c0` 类调整因子；
- 常见 `alpha` 来源包括 `OBI`、`OFI`、基差等。

文章最后补充，当前验证有效的策略使用跨所基差 `Basis` 的线性回归作为 `alpha`。

### 3. 报价层：围绕预测价格铺单

拿到预测价格后，脚本围绕这个价格决定：

- 挂单间隔价差；
- 挂单层级；
- 订单刷新时间；
- 库存模型；
- 动态 spread；
- 铺单等级。

作者使用 `GLFT` 模型，通过 `trades` 的变化计算时序价格到达深度，测算交易强度，并用前 `50-70` 档数据做参数拟合。

再结合交易强度生成动态 spread。

如果当前已有仓位，则先把仓位个数换算成名义持仓价值，再加权到铺单半差价上，让半差价发生倾斜，从而避免一次性积累过多库存。

作者提醒：线性仓位惩罚可能影响 `alpha` 有效性，并导致逆向成交。

### 4. 订单生成与订单 ID 映射

策略需要做订单生成和订单 ID 映射管理。

作者提到一个小技巧：直接使用 `price tick` 作为唯一 `orderID`，避免在同一价格重复下单。

### 5. 风控与 kill-switch

策略必须有风控和停机机制。

作者提到的停机条件包括：

- 交易强度异常；
- 有毒订单流；
- 必要时市价平仓；
- 停机并 `sleep 8hr`。

### 6. 监控与日志

最后需要监控日志系统，用来查看策略运行状态。

## 当前验证有效的组合

作者目前验证有效的策略组合是：

- 跨所基差 `Basis` 的线性回归作为 `alpha`；
- `GLFT` 模型做库存管理；
- 动态 spread 和铺单等级；
- 成交概率模型辅助调节报价。

其中成交概率模型不是用来预测市场是否成交，而是根据自身挂单的实际成交比例微调价差，让系统维持持续报价和目标 `order filled rate`。

## 评论区关键补充

`@Dogquant0` 提到：自己在 `GLFT` 中加入了泊松过程，用来处理库存风险。

这条评论的意义在于，做市脚本里的订单到达、成交强度、库存堆积，本质上都不是静态参数，而是随机过程。若要更严谨地建模成交到达和库存变化，单纯线性惩罚可能不够，需要引入更适合订单到达的随机过程模型。
